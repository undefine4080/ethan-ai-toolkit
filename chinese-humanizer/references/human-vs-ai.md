# 真人写作 vs AI 写作：深层特征分析

本文档不只告诉你"AI 会怎么写"，更要分析"为什么 AI 会这样写"，以及"如何判断和改写"。

---

## 核心洞察

**AI 写作的根本问题不是"错"，是"缺乏语境判断和自我审视"**

AI 知道很多词汇和句式，但不知道：
- 这个信息在当前语境下是否必要
- 这个情绪词汇是否过于书面化
- 自己是否在重复使用同一句式
- 这个修辞是否过于戏剧化

**真人写作的本质：会判断、会审视、会克制**

## 一、信息处理的度

### 1.1 信息标注强迫症

**AI 表现：**
```markdown
2021 年，知名数据可视化库 Recharts 在 GitHub Issue #3983 中报告了性能问题：
当存在大量刻度时，Recharts 性能显著下降，主要是频繁调用 `getStringSize`（基于
Canvas 的文本测量）。
```

**标注了什么：**
- 时间：2021 年
- 身份：知名数据可视化库
- 名称：Recharts
- 地点：GitHub
- 编号：Issue #3983
- 技术细节：`getStringSize`（基于 Canvas 的文本测量）

**问题本质：**
AI 把所有能标注的信息都标注了，像在写学术论文的引用，不管这些信息在当前语境下是否重要。

**真人写作：**

```markdown
Recharts 也遇到过这个问题——刻度太多时性能下降，因为频繁调用 measureText()。
```

**标注了什么：**
- 名称：Recharts
- 问题：刻度太多 → 性能下降
- 原因：频繁调用

**删掉了什么：**
- 时间：不重要（不影响理解）
- 身份："知名数据可视化库"（多余，Recharts 本身就说明了）
- 地点 + 编号：读者如果需要可以自己搜
- 部分技术细节：简化为 `measureText()`

---

### 判断标准

**问自己三个问题：**

1. **这个信息对理解有帮助吗？**
   - 是 → 保留
   - 否 → 删掉

2. **删掉后读者能理解吗？**
   - 能 → 删掉
   - 不能 → 保留

3. **这个信息是核心还是背景？**
   - 核心 → 保留并突出
   - 背景 → 简化或删掉

**应用到上面的例子：**

| 信息 | 对理解有帮助吗？ | 删掉后能理解吗？ | 核心还是背景？ | 决策 |
|------|-----------------|-----------------|---------------|------|
| 2021 年 | 否（时间不重要）| 能 | 背景 | ❌ 删掉 |
| "知名数据可视化库" | 否（多余）| 能 | 背景 | ❌ 删掉 |
| Recharts | 是 | 不能 | 核心 | ✅ 保留 |
| GitHub Issue #3983 | 否（可搜索）| 能 | 背景 | ❌ 删掉 |
| 频繁调用 measureText | 是 | 不能 | 核心 | ✅ 保留 |

---

### 1.2 信息完整性与表达效率

**AI 倾向：完整性优先**
```
时间 + 身份 + 地点 + 编号 + 完整描述 + 技术细节
```

**真人倾向：表达效率优先**
```
核心主体 + 核心问题（必要时加时间和地点）
```

**示例对比：**

| AI 版本 | 真人版本 | 差异分析 |
|---------|----------|----------|
| 2024 年，GitHub Issue #427 揭示了一个鲜为人知的问题：不同浏览器的 Canvas 文本测量结果存在显著差异。 | 不同浏览器的 Canvas 测量结果有差异，这是个已知的坑。 | 删掉时间、地点、编号；"鲜为人知的问题"→"已知的坑" |
| 2022 年，DebugBear 的性能分析博客中记录了这样一个警告：`[Violation] Forced reflow while executing JavaScript took 47ms` | DebugBear 记录过一个警告：`[Violation] Forced reflow while executing JavaScript took 47ms` | 删掉时间；"性能分析博客中记录了"→"记录过" |

---

### 1.3 信息密度 vs 可读性

**AI 问题：信息堆砌**
```markdown
2021 年，W3C CSSWG 的 GitHub Issue #3756 揭示了真相：CSS 规范要求浮动元素必须
"尽可能高"定位（CSS 2.1 第 9.5.1 节规则 8），而 Knuth 换行算法本质上可能导致某个
词（从而浮动边界）不是尽可能高。唯一能满足此规范的算法是贪婪算法。
```

一句话包含：
- 时间、组织、地点、编号
- 规范引用（CSS 2.1 第 9.5.1 节规则 8）
- 技术概念（Knuth 算法、贪婪算法）
- 逻辑推导

**真人改写：**
```markdown
W3C 规范有个要求：浮动元素要"尽可能高"定位。而 Knuth 算法可能导致浮动边界不够高。
所以浏览器只能用贪婪算法。
```

**改写原则：**
1. 删掉不影响理解的标注（时间、编号、完整规范引用）
2. 拆分长句：一句话说一件事
3. 简化逻辑推导：用"所以"连接，不用括号补充

---

### 1.4 改写清单

**检查每个信息标注：**

- [ ] 时间：是否重要？能否删掉？
- [ ] 身份描述：是否多余？能否简化？
- [ ] 地点 + 编号：读者需要吗？能否搜索到？
- [ ] 技术细节：是否过于完整？能否简化？
- [ ] 规范引用：是否必要？能否用简单表述替代？

**决策树：**
```
遇到一个信息标注
  ↓
问：这个信息对理解有帮助吗？
  ↓
否 → 删掉
  ↓
是 → 问：能用更简洁的方式表达吗？
       ↓
       能 → 简化表达
       ↓
       不能 → 保留原样
```

## 二、情绪表达的真实性

### 2.1 情绪词汇的书面化

**AI 常用情绪词（来自书面语料）：**
- 危言耸听、令人沮丧、令人震惊、深远影响
- 不可忽视、至关重要、举足轻重
- 深刻反映、充分体现、完美诠释

**真人常用情绪表达（来自口语习惯）：**
- 不是夸张、挺让人头疼、有点意外、影响很大
- 值得注意、很重要、挺关键
- 说明、体现、展示

**完整对照表：**

| AI 书面词 | 真人口语 | 使用场景 |
|-----------|----------|----------|
| 危言耸听 | 不是夸张 / 删掉 | 强调某事不是夸张 |
| 令人沮丧 | 挺让人头疼 / 有点无语 | 描述负面情绪 |
| 令人震惊 | 让人意外 / 没想到 | 表达惊讶 |
| 深远影响 | 影响很大 / 很重要 | 描述影响 |
| 不可忽视 | 值得注意 / 删掉 | 强调重要性 |
| 至关重要 | 很重要 / 关键 | 强调重要性 |
| 深刻反映 | 说明 / 体现 | 描述关系 |
| 充分体现 | 展示 / 说明 | 描述关系 |
| 完美诠释 | 很好地说明 | 描述关系 |
| 鲜为人知 | 不太被人注意 | 描述认知状态 |
| 戏剧性 | 意外 / 突然 | 描述变化 |

---

### 2.2 情绪的度：克制 vs 戏剧化

**AI 误判：以为"戏剧化" = "吸引人"**

```markdown
这不是危言耸听，而是真实发生在开发者控制台的警告。
```

```markdown
答案令人震惊：浏览器使用贪婪算法不是性能问题，而是规范约束！
```

**问题：**
- "这不是危言耸听" → 过度强调，制造戏剧感
- "答案令人震惊" → 强行制造悬念

**真人改写：**
```markdown
这不是夸张，是真实发生在开发者控制台的警告。
```

```markdown
原因是规范约束，不是性能问题。
```

**改写原则：**
1. 技术文章：让事实和数据自己说话，不必刻意制造情绪
2. 删掉"这不是危言耸听"、"令人震惊"等戏剧化修辞
3. 如果确实需要强调，用具体数据而不是形容词

**示例：**

| AI 戏剧化 | 真人克制 | 效果对比 |
|-----------|----------|----------|
| 这不是危言耸听，性能下降了 483 倍 | 性能下降了 483 倍 | 数据自己就有冲击力 |
| 令人震惊的是，只有 0.09ms | 只需要 0.09ms | 直接说事实更清晰 |
| 这个问题的深远影响不可忽视 | 这个问题影响很大 | 克制的表达更可信 |

---

### 2.3 情绪的自然度：制造 vs 流露

**AI 刻意制造情绪：**
```markdown
开发者反馈了一个让人沮丧的问题：动态高度虚拟列表在滚动时会出现"跳跃"现象。
```

"让人沮丧"是刻意加上去的情绪标签。

**真人自然流露情绪：**
```markdown
动态高度虚拟列表滚动时会"跳跃"——这个问题让人挺头疼的。
```

情绪是自然说出来的，不是贴标签。

**区别：**

| 刻意制造 | 自然流露 |
|---------|----------|
| 形容词在前：让人沮丧的问题 | 事实在前，情绪在后：这个问题挺让人头疼的 |
| 情绪作为定语：令人震惊的数据 | 情绪作为补充：数据让人意外 |
| 强调情绪：这真的很重要 | 让事实说话：这影响很大 |

**判断标准：**
问自己：这个情绪是"说出来的"还是"贴上去的"？

- 说出来的：问题 → 让人头疼（自然）
- 贴上去的：让人头疼的问题（刻意）

---

### 2.4 改写清单

**检查每个情绪表达：**

- [ ] 这个情绪词汇在对话中会说出来吗？
  - 会 → 保留
  - 不会 → 换成口语表达

- [ ] 这个情绪是自然流露还是刻意制造？
  - 自然流露 → 保留
  - 刻意制造 → 删掉或改写

- [ ] 这个戏剧化修辞有必要吗？
  - 有必要 → 保留
  - 没必要 → 删掉，让事实说话

## 三、句式的自我监控

### 3.1 句式重复检测

**AI 会不自觉重复同一句式：**

```markdown
如果告诉你，文本布局可以完全不碰 DOM，性能提升 50-100 倍，你相信吗？

...（中间隔了几段）...

如果告诉你，浏览器使用贪婪算法是规范要求，不是性能妥协，你相信吗？

...（又隔了几段）...

如果告诉你，这个问题至今没有完美解决方案，你相信吗？
```

**问题本质：**
AI 学会了某个"好用的句式"后会不自觉重复，因为它缺乏"自我审视"能力，不知道自己在重复。

**真人写作：**
- 会意识到："我刚用过这个句式，得换个说法"
- 同一篇文章中，相同句式最多出现 1 次
- 第二次会变着法说

**常见重复句式：**

| 句式模板 | AI 重复表现 | 真人变化 |
|---------|-------------|----------|
| 如果告诉你 xxx，你相信吗？ | 多次使用 | 第 2 次：说实话 / 想象一下 / 你可能觉得 |
| 这意味着什么？ | 多次使用 | 第 2 次：这说明 / 这代表 / 简单说就是 |
| 这不是 A，是 B | 多次使用 | 第 2 次：虽然 A，但实际上 B / 表面是 A，本质是 B |
| 值得注意的是 | 多次使用 | 第 2 次：有个细节 / 让我意外的是 / 还有个问题 |
| 综上所述 | 多次使用 | 第 2 次：总的来说 / 最后 / 总结一下 |

---

### 3.2 句式的模板化

**AI 学会"模板"后到处套用：**

```markdown
传统答案很简单：创建 DOM 元素 → 设置文本内容 → 渲染 → 调用 getBoundingClientRect() 读取高度。

**传统方案：** 先渲染再测量 → 卡顿
**估算方案：** 不准确 → 滚动条跳动
**Pretext 方案：** 预先测量 → 实时计算 → 流畅
```

**问题：**
- "xxx 很简单：A → B → C"模板
- "**标签：** 描述"模板

**真人写作：**
- 不会每个地方都用同一模板
- 会根据内容选择合适的表达方式
- 有的用流程，有的用描述，有的用对比

**判断标准：**
如果你的文章中同一模板出现 3 次以上，就需要变化了。

---

### 3.3 句式多样性库

**同一意思的多种表达：**

| 想要表达的意思 | 多种表达方式 |
|---------------|-------------|
| 强调某事 | 说实话 / 挺意外的 / 让我意外的是 / 没想到 / 说真的 |
| 提出问题 | 这意味着什么？/ 这说明什么？/ 简单说就是 / 换句话说 |
| 做对比 | 不是 A，是 B / 虽然看起来 A，但实际 B / 表面是 A，本质是 B |
| 引起注意 | 值得注意的是 / 有个细节 / 还有个问题 / 关键是 / 重点在于 |
| 做总结 | 综上所述 / 总的来说 / 总结一下 / 最后 / 简单说 |

---

### 3.4 改写清单

**检查句式重复：**

- [ ] "如果告诉你 xxx"出现了几次？（最多 1 次）
- [ ] "这意味着什么"出现了几次？（最多 1 次）
- [ ] "**标签：** 描述"格式出现了几次？（最多 2-3 次）
- [ ] "xxx → yyy → zzz"流程出现了几次？（最多 2-3 次）
- [ ] 同一模板出现了 3 次以上？→ 必须变化

**自我审视：**
写完后通读全文，标出所有相同的句式模板，问自己：
- 这个模板真的适合这里吗？
- 能否用其他方式表达？

## 四、戏剧化的克制

### 4.1 技术文章的修辞原则

**AI 误判：**
- 以为"吸引人" = "戏剧化"
- 以为"强调" = "用修辞"

**真人理解：**
- 技术文章的吸引力来自：具体数据、真实案例、清晰逻辑
- 强调的方式：让事实自己说话，不必刻意修辞

**示例对比：**

| AI 戏剧化 | 真人克制 | 分析 |
|-----------|----------|------|
| 这不是危言耸听 | 删掉 | 不必强调，直接说事 |
| 令人震惊的数据：0.09ms | 0.09ms | 数据本身就有冲击力 |
| 答案让人意外 | 原因是... | 不必制造悬念 |
| 这不是科幻，这是现实 | 这是 Pretext 带来的现实 | 不必对比科幻 |

---

### 4.2 强调词的使用频率

**AI 高频强调词：**
- 令人 xx、让人 xx、使人 xx
- 深远、巨大、显著、惊人
- 完美、极致、颠覆

**真人使用原则：**
- 技术文章：少用强调词，用具体描述代替
- 全文"令人/让人"不超过 2-3 处
- 用数据、案例、细节来强调，不用形容词

**替换规则：**

| 强调词 | 替换为 |
|--------|--------|
| 令人震惊的 | （直接展示事实或数据）|
| 让人沮丧的 | （描述具体问题，让读者自己感受）|
| 完美的 | 很好的 / 优秀的 |
| 极致的 | 很高的 / 顶级的 |
| 颠覆性的 | 突破性的 / 创新的 |

---

### 4.3 戏剧化修辞清单（该删的都删掉）

| 修辞 | 为什么删 | 如何改写 |
|------|---------|----------|
| "这不是危言耸听" | 过度强调，不必要 | 删掉，直接说事 |
| "这不是科幻，这是现实" | 刻意对比，制造戏剧感 | "这是 xxx 带来的现实" |
| "答案令人震惊" | 强行制造悬念 | 直接说答案 |
| "让人沮丧的问题" | 情绪标签 | 描述问题本身 |
| "深远影响" | 空洞强调 | 说具体影响是什么 |
| "划时代意义" | 夸大 | 说具体突破是什么 |

---

### 4.4 改写清单

**检查每个强调和修辞：**

- [ ] 这个"令人/让人"有必要吗？
  - 有必要 → 保留
  - 没必要 → 删掉或换成具体描述

- [ ] 这个戏剧化修辞有帮助吗？
  - 让文章更清晰 → 保留
  - 只是制造效果 → 删掉

- [ ] 能否用数据或事实代替形容词？
  - 能 → 替换
  - 不能 → 保留

## 五、语境判断能力

### 5.1 信息的必要性判断

**时间信息：何时需要？何时多余？**

| 需要 | 多余 |
|------|------|
| 从 2021 年到现在，问题还没解决（时间有对比意义）| 2021 年，某个 issue 报告了...（时间不重要）|
| 这项技术在 2024 年取得突破（时间是里程碑）| 2024 年的研究发现...（时间不影响理解）|
| 经过 3 年开发（时间说明工作量）| 在 2022 年的时候...（时间只是背景）|

**来源信息：何时完整标注？何时简略？**

| 完整标注 | 简略标注 |
|---------|----------|
| W3C CSSWG 的 Issue #3756 明确规定...（权威来源，读者可能需要查阅）| 有人提过这个问题...（普通来源）|
| 根据 DebugBear 的性能分析...（专业分析）| 有个 issue 讨论过...（读者可自行搜索）|

**编号信息：何时重要？何时干扰？**

| 重要 | 干扰 |
|------|------|
| React Issue #610 至今未解决（说明问题的持续性）| GitHub Issue #3983 报告了...（编号不重要）|
| 参见 RFC 3986 第 3.2 节（规范引用，需要精确）| 参见某个 issue（编号多余）|

---

### 5.2 表达方式的选择

**正式 vs 口语：根据文章类型判断**

| 文章类型 | 表达方式 |
|---------|----------|
| 学术论文 | 正式、完整、规范 |
| 技术博客 | 混合：核心技术内容正式，引言和总结口语 |
| 教程文档 | 口语、清晰、步骤化 |
| 个人分享 | 口语、随意、有个性 |

**完整 vs 简洁：根据读者需求判断**

| 读者需求 | 表达方式 |
|---------|----------|
| 深度理解原理 | 完整、详细、有背景 |
| 快速解决问题 | 简洁、直接、步骤化 |
| 评估是否使用 | 重点突出、对比清晰 |

**戏剧 vs 平实：根据内容性质判断**

| 内容性质 | 表达方式 |
|---------|----------|
| 意外的发现、反直觉的结论 | 可以稍加强调（"让我意外的是"）|
| 常规技术、标准做法 | 平铺直叙，不必强调 |
| 性能数据、具体案例 | 让数据自己说话 |

## 六、格式与结构

### 6.1 标题层级：不要教科书式的完美

| AI 特征 | 真人写作 |
|---------|----------|
| 严格的 h1/h2/h3 层级 | 混用层级，甚至直接用粗体当标题 |
| "一、引言"、"二、核心内容" | "卷首语"、"先说两句"、"核心突破" |
| 标题对仗工整 | 标题长度不一，风格各异 |
| 每个标题都是完整陈述 | 标题可以是问句、短语、甚至吐槽 |

**改写策略：**
- 删除标题序号（一、二、三 → 直接用标题文字）
- 打破层级严格性（h2 下可以直接跳到 h4）
- 允许标题风格不统一（有的正式，有的口语）

---

### 6.2 段落长度：参差才自然

| AI 特征 | 真人写作 |
|---------|----------|
| 段落长度相近，追求平衡 | 段落长短悬殊极大 |
| 每段结构完整 | 有些段落只有一句话，甚至一个词 |
| 段落之间过渡平滑 | 有时突然转折，没有过渡 |

**改写策略：**
- 不要刻意平衡段落长度
- 允许出现超短段落（1-2 句话）
- 删除不必要的过渡句，让段落自然跳跃

---

### 6.3 口语化注入

**第一人称视角：**
- 把"本文认为"→ "我觉得"、"在我看来"
- 把"值得注意的是"→ "让我意外的是"、"我发现"

**语气词：**
- 适当添加："嘿"、"你看"、"说真的"、"其实"

**括号备注（吐槽神器）：**
- 在合适的地方添加括号备注
- 内容可以是：吐槽、调侃、自嘲、题外话
- 例如："（就像……一样）"、"（也许是我太敏感？）"

---

### 6.4 格式保留而非清理

**不要过度清理格式：**
- ❌ 不要删除所有加粗（保留 3-5 处）
- ✅ 保留合适的 emoji
- ✅ 保留有价值的列表（尤其长短不一的列表）
- ✅ 保留装饰性元素（分隔线等）

**判断列表是否保留：**
- 如果列表让内容更清晰可扫视 → 保留
- 如果列表只是强行拆分句子 → 改为段落
- 如果列表项长短不一、风格随意 → 保留（这是真人写作特征）

## 七、实操工具

### 7.1 AI 特征快速检测清单

**信息标注（5 项）：**
- [ ] 时间标注：每个都重要吗？
- [ ] 来源标注：每个都必要吗？
- [ ] 编号标注：每个都有用吗？
- [ ] 身份描述：每个都不多余吗？
- [ ] 信息密度：是否过于堆砌？

**情绪表达（4 项）：**
- [ ] 情绪词汇：是否书面化？
- [ ] 情绪自然度：是流露还是制造？
- [ ] 戏剧化修辞：是否过度？
- [ ] 强调词频率：是否过多？

**句式使用（3 项）：**
- [ ] 句式重复：同一句式出现几次？
- [ ] 模板化：同一模板出现几次？
- [ ] 句式多样性：是否足够丰富？

**整体效果（3 项）：**
- [ ] 活人感：能否感到真人在写？
- [ ] 不规整度：格式是否过于教科书？
- [ ] 原意保真度：核心信息是否完整？

### 7.2 改写决策树

**遇到信息标注：**
```
这个信息对理解有帮助吗？
  ↓
否 → 删掉
  ↓
是 → 能用更简洁的方式表达吗？
       ↓
       能 → 简化表达
       ↓
       不能 → 保留原样
```

**遇到情绪词汇：**
```
这个情绪词在对话中会说吗？
  ↓
不会 → 换成口语表达或删掉
  ↓
会 → 这个情绪是自然流露还是刻意制造？
       ↓
       刻意制造 → 删掉或改写
       ↓
       自然流露 → 保留
```

**遇到句式模板：**
```
这个模板在文章中出现了几次？
  ↓
1 次 → 保留
  ↓
2 次 → 考虑变化
  ↓
3 次以上 → 必须变化
```

### 7.3 常见问题速查表

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| 每个引用都带年份 | 信息标注强迫症 | 只在时间重要时标注 |
| 用"危言耸听"等书面词 | 情绪词汇书面化 | 换成"不是夸张"或删掉 |
| 同一句式重复 3 次 | 缺乏自我监控 | 第 2 次开始变化表达 |
| 过多"令人/让人" | 过度戏剧化 | 删掉或用具体描述替代 |
| 信息堆砌 | 完整性优先 | 简化背景信息，突出核心 |

## 总结：去 AI 化的核心

**AI 写作的根本问题：**
- 缺乏语境判断能力
- 缺乏自我审视能力
- 缺乏克制和变化

**真人写作的本质：**
- 会判断：知道什么信息重要，什么可以删
- 会审视：知道自己是否在重复、是否自然
- 会克制：不过度戏剧化，让事实说话

**改写目标：**
不是让文章完美，是让文章真实。
不是删掉所有修饰，是删掉不必要的修饰。
不是让文章口语化，是让文章自然化。

**记住：**
AI 写作像在"完成任务"，真人写作像在"与人对话"。
保留不完美，才是真实。
