# 工程范式 / 优秀实践

这份文档是**与语言无关**的通用范式。语言/框架特化部分（比如 TS 的判别联合、React 的 hooks 规则）放在 `frameworks/` 里。

---

## 核心判断问句

1. **这段代码用了继承的地方，是否能用组合替代？**
2. **这块逻辑是否是 composable 的？能不能被另一个场景直接复用？**
3. **类型声明是否完整？有没有 `any` / 弱类型漏洞？**
4. **副作用是否被隔离？纯函数和副作用函数是否分开？**
5. **可测试性如何？这段代码有没有被写成难以测试的样子？**

---

## 范式 1：组合优于继承（Composition over Inheritance）

### 为什么组合更好

- 继承是**编译期**的强绑定，组合是**运行期**的灵活组装
- 继承的"菱形问题"、"脆弱基类问题"会随着层级深度指数爆炸
- 组合更符合"对象是行为的集合"这个直觉

### 坏味道

- 类继承链超过 2 层（`Base → Middle → Concrete`）
- 为了共享几个方法，让两个本质不同的类共享同一个基类
- 在基类里塞"可能被子类覆盖"的钩子方法（模板方法模式被滥用）

### 更好的方式

- 用 **mixin / 组合函数 / hooks / composables / trait** 把能力注入对象
- 用**依赖注入**把行为作为参数传入，而不是通过继承覆盖

### 例外

不是说继承就永远错。合理的继承场景：
- 语言/框架要求必须继承（如 Vue 2 的 `extends Vue`、旧式 React class component）
- 类型层面的"is-a" 关系确实存在且稳定（Error 的子类）

## 范式 2：Composable（可组合性）

"**每段逻辑都应该能被独立抽出、独立复用、独立测试**"。

### 判断一段代码是否 composable

- **输入输出清晰**：从签名能看出全部依赖
- **无隐藏依赖**：不依赖全局状态、不依赖调用顺序
- **副作用显式**：要么是纯函数，要么副作用在函数名里明示（`loadUser` 明显有 IO）

### 反模式

- **全局单例毒化**：业务代码直接 `import userStore` 操作全局状态，函数签名看不出来它修改了什么
- **隐式依赖**：一个函数必须在 `setupXxx()` 之后调用才能正确工作，但这个顺序约束只存在于开发者脑子里
- **时序耦合**：A 必须在 B 之前调用，否则崩溃，但代码里没任何保护

### 好例子
- React 的自定义 hooks
- Vue 3 的 composables
- 纯的 transformer 函数（输入→输出，无副作用）

## 范式 3：类型完整性

**类型是最廉价的文档**。放弃类型就是放弃未来维护时的安全网。

### 强信号的类型异味

- **`any` 滥用**：特别是作为参数/返回值类型。`any` 会像病毒一样传染整个调用链
- **类型断言 `as` 滥用**：每次 `as Foo` 都是在对类型系统说"相信我"，过度使用等于裸奔
- **类型收窄缺失**：`if (x)` 之后还能传 `null`；用判别联合代替
- **魔法字符串**：本应是枚举 / 联合类型字面量的地方用了裸字符串
- **类型漂移**：同一个概念在不同文件里有不同的类型定义

### 正向特征

- 函数签名即文档，不看实现就能写调用
- 数据源头（API 响应、配置）有严格类型定义，且在边界处校验（zod / io-ts）
- 状态用**判别联合**（discriminated union）表达，而不是多个独立布尔
- 泛型用得克制：**只在真的通用时才用**，不要为了"看起来专业"硬加泛型

### 语言相关的细节
TS 的 `never` / `unknown` / `satisfies` 等特化话题，放在 `frameworks/typescript.md` 或 `frameworks/<framework>.md` 里谈。

## 范式 4：副作用隔离

**纯计算 vs 副作用必须分层**。混在一起的代码不可测试、不可推理、难复用。

### 好的分层
- 最内层：纯函数（数据转换、业务规则计算）
- 中间层：编排（调度多个纯函数）
- 最外层：副作用（网络、IO、DOM、全局状态修改）

### 坏味道
- 一个函数里先改状态、再请求网络、再计算、再改状态（没有阶段划分）
- 数据转换函数里夹杂着 `console.log` 或修改入参
- 业务规则判断里藏着网络请求

---

## 范式 5：显式优于隐式

- **显式错误处理** 优于默默吞掉异常
- **显式返回类型** 优于依赖推断（公共 API 层）
- **显式依赖** 优于依赖上下文或 this
- **显式边界检查** 优于"信任输入"

但注意：不要走极端把所有东西都显式化。局部短生命周期的变量该推断就推断，不要反而变啰嗦。

---

## 范式 6：可测试性

**一段代码难以测试，往往是架构有问题的信号**。

### 难测试的症状
- 函数依赖全局状态 / 单例 / 网络
- 函数包含太多副作用混在一起
- 组件把业务逻辑和 UI 渲染深度耦合

### 易测试的特征
- 纯函数可以直接单测
- 副作用通过参数/依赖注入，可以替换成 mock
- UI 和业务分离，业务逻辑可以脱离 UI 测试

## 严重度定级参考

| 现象 | 建议严重度 |
|---|---|
| 大范围 `any` 滥用导致类型安全失效 | 🟡 Major |
| 应该用状态机却用布尔堆 / 类型表达力差 | 🟡 Major |
| 继承链过深且可用组合替代 | 🟡 Major |
| 副作用和纯计算混在一起的核心函数 | 🟡 Major |
| 单点 `as` 断言、单处隐式依赖 | 🟢 Minor |
| 泛型略过度、命名不够 composable | 💭 Nit |
