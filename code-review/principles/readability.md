# 可读性 / 可扩展性 / 可维护性

AI 能写无限多的代码，但**人类读不懂的代码无法被持续维护**。可读性不是装饰，是工程的生命线。

---

## 核心判断问句

1. **一个刚接手项目的新人，读这段代码需要多少上下文？**
2. **变量/函数/文件/模块的名字，是否精确反映了它的作用？**
3. **如果不看实现只看签名/命名，我能不能猜对行为？**
4. **六个月后的自己，会感谢当时的自己这样写吗？**
5. **改一个需求，需要修改几处代码？" 影响半径"是否可控？**

---

## 命名——最被低估的可读性因素

### 好命名的标准

- **精确**：`userList` 优于 `list`，`activeUserCount` 优于 `num`
- **语义单一**：一个名字只对应一个含义，不要在不同上下文里含义漂移
- **一致性**：同一概念全项目使用相同术语（不要一会儿 `user` 一会儿 `member` 一会儿 `account`）
- **反对缩写**：除非是项目公认的领域术语或极其常见的（`id`、`url`、`btn` 也别用，写 `button`）

### 常见命名坏味

- `data`、`info`、`result`、`temp`、`obj`、`item` —— 毫无信息量
- `doSomething`、`handleStuff`、`processData` —— 含糊的动词
- `flag`、`flag2` —— 布尔值该用 `is/has/can/should` 前缀
- `newUser` / `oldUser` 混用 —— 在异步场景下会混淆，用 `nextUser` / `prevUser` 更准
- **匈牙利命名法**（`strName`、`bIsAdmin`）—— 在强类型语言里是噪音

## 模块边界与"影响半径"

评审时要跨文件思考：**改一个需求，影响面有多大？**

### 好的边界
- 改一个业务需求 → 只动一个 feature 目录
- 改一个 UI 组件样式 → 只动这个组件
- 加一个新字段 → 顺着类型定义的"导航"就能找到所有需要改的地方

### 坏的边界
- 改登录逻辑，要动 5 个不相关目录下的文件
- 加一个字段，要在 N 个地方手动同步，漏一个就 bug
- 一个组件的变化要求调用方也跟着改（"**泄漏的抽象**"）

## 目录结构的可读性

### 好的目录结构
一眼看出项目的**领域划分**。例如：
```
features/
  auth/
  checkout/
  profile/
shared/
  ui/
  utils/
```

### 坏的目录结构
按**技术类型**切分到极致：
```
components/
  AuthLoginForm.tsx
  CheckoutCart.tsx
  ProfileAvatar.tsx
hooks/
  useAuthLogin.ts
  useCheckoutCart.ts
  useProfileAvatar.ts
```
这种结构让同一业务的代码散落各处，改一个功能要跳好几个目录。

> 规则：**领域（feature）分组 > 技术类型分组**。除非是真正跨领域共享的，否则代码应该和它的业务领域住在一起。

## 注释的正确用法

- **好注释**：解释"**为什么**"（为什么用这个特殊值、为什么绕这个弯、为什么不用更直观的写法）
- **坏注释**：解释"**是什么**"（代码已经说清楚的事情，再复述一遍）

```
// 坏：复述代码
// 把 user 的 age 加 1
user.age = user.age + 1;

// 好：解释为什么
// 业务规定虚岁从 1 开始算，后端传的是周岁，前端需要 +1 展示
user.age = user.age + 1;
```

**TODO / FIXME 没写理由和期限的，等于 TODO 永远不会被做**。合理的 TODO：`TODO(2026-Q2): 等后端支持分页后移除`。

## 可扩展性——但不是"预留扩展点"

注意：**可扩展 ≠ 预留插件位**。真正的可扩展性来自：

- **清晰的边界**：增量加功能不破坏现有逻辑
- **正交性**：各模块之间互不干扰，可以独立演进
- **稳定的契约**：类型/接口定义清楚，调用方不用关心内部

而"预留扩展点"（提前 new 一个策略模式）往往是过度设计（见 `architecture.md`）。两者的区别是：

| 真·可扩展 | 假·可扩展 |
|---|---|
| 基于现有抽象的自然延伸 | 提前创造的抽象 |
| 边界清晰，改动局部 | 边界模糊，改动蔓延 |
| 不需要扩展时不占成本 | 即使没扩展也在维护 |

---

## 好可读性的正向特征

- 文件名 / 函数名一看就懂
- 读一段代码不用反复向上回看含义
- 错误处理和正常路径清晰区分
- 状态流转明确（不是一堆布尔值的笛卡尔积）
- 关键决策处有"为什么"的注释

## 严重度定级参考

| 现象 | 建议严重度 |
|---|---|
| 命名完全误导、读代码会得出错误理解 | 🟡 Major |
| 目录结构让改动影响半径失控 | 🟡 Major |
| 注释缺失但代码有非直觉行为 | 🟡 Major |
| 命名不够精确但能猜 | 🟢 Minor |
| 偶尔出现的缩写或 `data` 之类 | 💭 Nit |
