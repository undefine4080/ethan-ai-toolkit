# 架构优雅性 / 过度设计识别

这是评审的第一把尺子。**架构优雅 ≠ 层次多**，恰恰相反——好的架构往往是"刚刚够用"的架构。

---

## 核心判断问句（评审时问自己）

当看到一层抽象、一个接口、一段"为将来预留"的代码时：

1. **这一层抽象，删掉会怎样？** 如果删掉只是少写几行代码、没有任何其他代价，这层抽象就是负担。
2. **如果只有这一个实现，为什么要接口？** 单实现接口是典型的过度设计信号。
3. **这个"扩展性"有第二个具体场景吗？** 想象中的扩展点，99% 用不上。
4. **如果一个新人接手，他需要跳几次定义才能读懂这段逻辑？** 超过 3 次就值得警惕。
5. **这个模块的职责能用一句话说清吗？** 说不清的多半是上帝模块。

---

## 过度设计的四个典型信号

### 信号 1：抽象层超过使用次数

一个基类只有一个子类、一个接口只有一个实现、一个工厂只造一种对象——这都是"先抽象后使用"的痕迹。

> YAGNI 原则：You Aren't Gonna Need It。抽象应该在**第二次**出现相似需求时提取，而不是预想未来。

### 信号 2：提前扩展点

代码里留着"以后可能要换"的插件位、策略模式、配置化 —— 从未被换过，而且可以预见也不会被换。

识别方法：看 git log。如果一个"扩展点"从提交至今半年以上没有新增实现，99% 是过度设计。

### 信号 3：配置即编程

用 JSON/YAML 把本来简单的 `if / else` 拆成"配置驱动"。配置本身反而变成一种 DSL，读懂配置比读懂代码还累。

> 经验法则：如果配置的分支数量 ≤ 3，就用代码。配置的成本往往高于它节省的灵活性。

### 信号 4：薄包裹（Thin Wrapper）

包了一层第三方库（axios、dayjs、lodash），理由是"以后好换"。但：
- 你永远不会换
- 即使换了，薄包裹也覆盖不了新库的全部能力
- 包裹层本身成为新的维护负担

**唯一合理的包裹**：需要在调用前后统一注入逻辑（鉴权、日志、错误转译），且这个逻辑是项目级的约束。

## 架构级反模式（需要跨文件评审）

### 上帝模块 / 上帝组件
一个文件 / 类 / 组件承担了太多职责。典型表现：
- 文件超过 500 行且不是配置/类型定义
- 一个组件内部管理了网络请求 + 状态 + 业务逻辑 + 渲染 + 格式化
- 一个 store / service 被 N 个毫不相关的模块共同依赖

### 循环依赖
A 依赖 B，B 又依赖 A（可能通过 C 间接）。这是架构腐化的强烈信号——职责划分一定出了问题。

### 依赖方向错误
高层模块依赖低层模块是正常的；**低层模块反向依赖高层**（如 utils 里 import 了某个业务页面）就是职责错位。

### 职责分层混乱
典型表现：
- UI 组件里直接调接口（没有 service / hook 层）
- Service 层知道了 UI 的结构（返回前端专用字段名）
- 业务逻辑散落在 UI 组件里而不是集中在领域层

---

## 好架构的正向特征（避免只写负面清单）

评审时如果发现这些，**必须写进报告的"亮点"章节**：

- **职责边界清晰**：看一个文件名就能猜到它做什么，而且猜得对
- **依赖方向单向**：高层 → 低层，没有循环
- **公共逻辑下沉克制**：只有**被用到两次以上**的才下沉
- **扩展点**：只在**有真实第二场景**时才出现
- **删一行代码能看出变化**：没有无意义的中间变量、无用的抽象包装

## 严重度定级参考

| 现象 | 建议严重度 |
|---|---|
| 循环依赖、明显的职责错位 | 🟡 Major |
| 上帝模块（已经成为维护瓶颈） | 🟡 Major |
| 过度设计（有抽象但未来也不会用到） | 🟢 Minor |
| 薄包裹（不影响功能只是冗余） | 🟢 Minor |
| 配置即编程（可读性差） | 🟢 Minor / 🟡 Major（看严重程度） |

**架构问题极少是 🔴 Critical**（Critical 留给会阻塞合并的事——安全漏洞、数据丢失、明显 bug）。
