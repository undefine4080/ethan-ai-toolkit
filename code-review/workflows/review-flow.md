# 主审查流程

**自顶向下，由粗到细**。目标是在有限 token 内建立全局心智模型，再对热点深读。

---

## 前置条件

进入本流程前，SKILL.md 启动阶段应该已经完成：
- 用户声明的技术栈被确认
- 对应的 `frameworks/*.md`（含依赖）已加载
- `principles/` 下 4 份文档已全量加载

如果上述任何一项未完成，**退回 SKILL.md 走启动流程**。

---

## Step 1：建立项目画像（Fast Scan）

**目标**：用最少的读操作建立项目心智模型。

**操作顺序**：

1. **看根目录结构**（`list_dir` 根目录一次）
   - 判断：SPA？monorepo？组件库？业务应用？
   - 看是否有 `apps/`、`packages/`（monorepo 信号）
   - 看是否有 `src/` 的组织方式

2. **读依赖声明**（`package.json`）
   - 关注 dependencies 的主要库（状态管理、UI 库、数据层、路由）
   - 关注 devDependencies（测试、lint、构建工具）
   - 看 scripts，理解项目怎么跑

3. **读关键配置**（按需）
   - TS 项目 → `tsconfig.json`（strict 是否开？path alias？）
   - Next → `next.config.*`
   - 有 `eslint.config.*` / `.eslintrc` → 大致看严格度

4. **看入口和路由**
   - Next App Router → `app/` 目录结构
   - React SPA → `src/main.tsx` / `src/App.tsx`

**时间盒**：这一步应该只用几次读操作，不要在这里花太多 token。**目的是建立地图，不是详读。**

**产出**：在心里（或简短写下）形成：
- 项目类型（业务应用 / 库 / 工具）
- 规模级别（小 <50 文件 / 中 50-500 / 大 500+）
- 主要栈
- 明显的目录组织方式
- 值得深读的 3-5 个热点

---

## Step 2：选定热点深读（Targeted Deep Read）

**不要穷举**。token 预算有限，穷举所有文件会导致每个都只能扫一眼，结果都是表面评语。

**挑选热点的依据**（按优先级）：

1. **入口文件**：根 layout / App.tsx / 主路由定义 —— 决定整体架构
2. **最大的业务模块**：通常是项目价值最高的地方
3. **状态管理中心**：store / context provider
4. **看起来最复杂的文件**：通过 `list_dir` + 大致文件大小判断
5. **跨多个地方被 import 的"公共基础设施"**：utils、hooks、components/ui
6. **用户特别点名的目录**（如果有）

**不要读的**：`node_modules/`、`dist/`、`.next/`、`build/`、`*.min.*`、`pnpm-lock.yaml`、大的数据文件、自动生成文件。

**深读每个热点时的关注点**：

对照已加载的 `principles/` + `frameworks/`，做**多维度交叉检查**：

- **架构维度**（`principles/architecture.md`）
- **简洁维度**（`principles/simplicity.md`）
- **可读维度**（`principles/readability.md`）
- **范式维度**（`principles/paradigms.md`）
- **框架特化维度**（`frameworks/<name>.md`）

对每个发现做一次**严重度判断**（见 `principles/*.md` 里的严重度参考表）。

---

## Step 3：跨文件的架构洞察

前两步都是看单点。**真正有价值的评审往往在跨文件层面**。

**跨文件要找的东西**：

1. **循环依赖 / 依赖方向错误**
   - 业务模块之间是否有不该有的依赖？
   - 底层 utils 是否 import 了业务代码？

2. **重复实现**
   - 同一种能力（比如日期格式化、API 错误处理）是否被多个地方各自实现？
   - 为什么没有统一？是缺少基础设施还是没意识到？

3. **职责散落**
   - 同一个业务的逻辑是否散落在多个不相关目录？（可读性 principles 里讲过的"坏目录结构"）

4. **抽象分层是否一致**
   - 项目是否约定了分层（比如 components / hooks / services / stores）但某些文件不遵守？

5. **一致性**
   - 项目里同类事物的处理方式是否一致？（比如有的地方用 react-query 有的地方手写 fetch）
   - 不一致不一定是 bug，但是架构腐化的信号

---

## Step 4：思考"缺失的东西"（Blind Spots）

这一步最容易被跳过，但往往是评审里最有价值的部分。**AI 总是说"我看到的问题"，真正有经验的 reviewer 会说"我没看到的东西"**。

对照清单，过一遍：

- **错误处理**：是否有统一的 error boundary？API 错误如何传递给用户？
- **Loading / Empty / Error 三态**：列表、详情、表单是否都处理了？
- **类型完整性**：API 边界（请求/响应）是否有类型定义？是否在运行时校验（zod 等）？
- **测试**：有没有测试？测了什么？测得合理吗？
- **可观测性**：是否有日志、埋点、错误上报？（对业务项目重要）
- **安全**：输入校验？XSS / CSRF / 权限控制？（OWASP Top 10 关键项）
- **可访问性（a11y）**：键盘操作、语义 HTML、aria 属性？
- **性能考量**：大列表是否虚拟化？图片是否优化？bundle 是否过大？
- **国际化 / 多语言**（如果业务需要）

**注意**：不是每一项都必须有。评审时要**结合项目类型判断**——一个内部工具不需要强调 a11y 和 i18n，但需要强调错误处理和类型完整性。

---

## Step 5：整理发现 + 应用报告纪律

在写入报告之前，把 Step 2-4 的发现整理一下：

1. **合并相似问题**：如果 5 个文件都有同样的 useEffect 滥用，合并成一条，举 2-3 个代表即可
2. **应用严重度校准**：
   - **🔴 Critical 全报告至多 3 条**（硬上限，超过必须降级或合并）
   - Critical 只给安全漏洞、数据丢失、明显 bug、违反框架硬约束（如 Rules of Hooks）
   - 架构异味 → 最高 🟡 Major
   - 个人偏好 → 必须标 💭 Nit
3. **给每条问题写"为什么"**：没有 why 的问题不算一条问题
4. **收集亮点**：项目肯定有做得好的地方，至少列 2-3 条
5. **准备 Blind Spots 章节**：Step 4 里思考的缺失之物

---

## Step 6：输出报告

按 `report-template.md` 的骨架写入：

```
<cwd>/.ai/code-review/review-<YYYY-MM-DD-HHmm>[-scope].md
```

- 目录不存在则创建
- 时间用本地时间，精确到分
- scope 仅在用户指定了子目录评审范围时附加（slug 化：`src/features/auth` → `src-features-auth`）

报告写完后，**对话里只给摘要**：
- 一段话总体评价
- Critical 问题数量（至多 3 条）
- 报告文件的完整路径

**不要**把完整报告贴进对话。

---

## 质量自检（报告落盘前的最后一步）

在生成报告文件之前，过一遍自检清单：

- [ ] 是否给了具体的代码修改建议？（**违规**：只能给方向和问题）
- [ ] Critical 是不是超过 3 条？
- [ ] 每条问题有没有解释"为什么"？
- [ ] 有没有"亮点"章节且内容真实？
- [ ] 有没有"Blind Spots"章节？
- [ ] 有没有把个人偏好包装成客观问题？
- [ ] 有没有评审用户没声明的技术栈？（**违规**：超出能力边界）

任一项不通过，回去调整。
